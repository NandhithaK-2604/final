> I need to add a dynamic Batch Approval Timeline / Batch Status Stepper to my existing SavnyaPay application.

Do not redesign the existing application. Do not disturb the existing sidebar, navigation, Payee Details table, batch layout, API structure, or existing functionality unless required for this feature.

The timeline must appear only on the Manage → Batch Details page, directly above the existing “Payee Details” table.

Use a compact horizontal stepper so it does not make the page unnecessarily tall.


---

1. Approval workflow must be dynamic

A batch can have either:

1 approval level

2 approval levels


Do NOT hardcode Approver 1 and Approver 2 for every batch.

The backend should determine the number of approval levels configured for that batch.

Example:

approvalLevels = 1

Timeline:

Created → Validated → Submitted → Approver 1 → Processing

For:

approvalLevels = 2

Timeline:

Created → Validated → Submitted → Approver 1 → Approver 2 → Processing

The frontend should dynamically render the appropriate number of approval steps.


---

2. Normal 2-level approval

When Approver 1 approves:

✓ Created
→
✓ Validated
→
✓ Submitted
→
✓ Approver 1 — Approved
→
🔵 Approver 2 — Pending
→
○ Processing

Approver 2 should become the current active approval level.


---

3. Approver 2 rejects

If Approver 2 rejects the batch, DO NOT remove or overwrite the previous Approver 1 approval.

Show:

✓ Created
→
✓ Validated
→
✓ Submitted
→
✓ Approver 1 — Approved
→
✕ Approver 2 — Rejected
→
↩ Returned to Approver 1 — Pending

Display the rejection reason if available.

Example:

Rejected by Approver 2
Reason: Beneficiary account verification failed


---

4. Approver 1 approves again

If the rejected batch is returned to Approver 1 and Approver 1 approves it again, do not overwrite the previous approval event.

Add a new approval history event.

The timeline should then represent:

✓ Created
→
✓ Validated
→
✓ Submitted
→
✓ Approver 1 — Approved
→
✕ Approver 2 — Rejected
→
↩ Returned to Approver 1
→
✓ Approver 1 — Re-approved
→
🔵 Approver 2 — Pending
→
○ Processing

Approver 2 should become pending again.

This cycle must be repeatable if the business workflow allows it.


---

5. One-level approval

For a batch with only one approval level:

✓ Created
→
✓ Validated
→
✓ Submitted
→
🔵 Approver 1 — Pending
→
○ Processing

If Approver 1 rejects:

✓ Created
→
✓ Validated
→
✓ Submitted
→
✕ Approver 1 — Rejected

If the business rule returns the batch to Approver 1, show:

✕ Approver 1 — Rejected
→
↩ Returned to Approver 1 — Pending

Do not show Approver 2 anywhere for a one-level batch.


---

6. Backend implementation

Do not hardcode the timeline in React/frontend.

Store approval/history events in the backend so that the timeline represents the actual batch history.

Create an appropriate entity/table such as:

BatchHistory / ApprovalHistory

Suggested fields:

id
batchId
action
approvalLevel
performedBy
timestamp
remarks

Example records:

CREATED
VALIDATED
SUBMITTED
APPROVED - LEVEL 1
REJECTED - LEVEL 2
RETURNED_TO_LEVEL_1
RE_APPROVED - LEVEL 1

Preserve all historical events. Never overwrite previous approval/rejection records.


---

7. API

Add an appropriate backend endpoint to retrieve the history for a batch, for example:

GET /batches/{batchId}/history

Follow the existing Controller → Service → Repository architecture already used in the project.

If DTOs are used in the existing project, create/use an appropriate DTO rather than exposing the entity directly.

Return the approval level, action/status, timestamp, user, and remarks needed by the frontend.


---

8. Frontend

On the existing Manage → Batch Details page:

Batch ID
Batch information
↓
Batch Status / Approval Timeline   ← ADD HERE
↓
Payee Details                      ← KEEP EXISTING
↓
Total Payees / Total Amount        ← KEEP EXISTING

Do not create a separate page.

Do not create a large history table.

Do not disturb the existing Payee Details table.

Use a compact horizontal stepper with:

Green check = completed

Blue highlighted step = current/pending

Red X = rejected

Neutral gray circle = upcoming

Return/rework indicator for returned batches


Show timestamps underneath the steps where space permits.

On smaller screens, make the stepper horizontally scrollable or adapt responsively.


---

9. Important business logic

The timeline must represent actual history, not just the current status.

Example:

Approver 1 approved
↓
Approver 2 rejected
↓
Returned to Approver 1
↓
Approver 1 approved again
↓
Approver 2 pending

The previous Approver 1 approval must remain visible in the history.

The current approval level must always be determined by the backend.
