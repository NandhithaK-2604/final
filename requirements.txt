Implement a role-based notification system in the existing SavnyaPay application.

IMPORTANT:
- First inspect the existing backend and frontend architecture.
- Reuse the existing authentication, roles, batch workflow, approval, rejection, revert, and payment-date logic.
- Do not create duplicate business logic.
- Do not hardcode notifications.
- Notifications must be generated from actual backend workflow events.
- Do not break existing functionality.

==================================================
1. NOTIFICATION BELL
==================================================

Use the existing notification/bell icon in the application header.

When the user logs in, the notification bell should show the unread notification count.

Example:

🔔 3

The count must come from the backend.

When the user clicks the bell, show a notification dropdown containing the latest notifications.

Include:

- Notification title
- Notification message
- Batch ID where applicable
- Time/date
- Read/unread state
- "Mark all as read"
- "View all notifications"

Unread notifications should be visually highlighted.

==================================================
2. ROLE-BASED NOTIFICATIONS
==================================================

Notifications must be sent based on the logged-in user's role and the batch workflow.

Do NOT send all notifications to every user.

Use the existing role and approval assignment logic.

--------------------------------------------------
CREATOR SUBMITS BATCH
--------------------------------------------------

When the creator successfully submits a batch for approval:

Batch status:
PENDING_LEVEL_1

Send a notification to the assigned Level 1 approver:

Title:
"Approval Required"

Message:
"Batch {batchId} has been submitted for your approval."

Optionally notify the creator:

"Batch {batchId} has been successfully submitted for approval."

--------------------------------------------------
LEVEL 1 APPROVES
--------------------------------------------------

When Level 1 approves:

Batch status:
PENDING_LEVEL_2

Send notification to the assigned Level 2 approver:

Title:
"Approval Required"

Message:
"Batch {batchId} has been approved at Level 1 and is awaiting your approval."

Send notification to the creator:

Title:
"Level 1 Approved"

Message:
"Batch {batchId} has passed Level 1 approval and is now awaiting Level 2 approval."

--------------------------------------------------
LEVEL 1 REJECTS
--------------------------------------------------

When Level 1 rejects:

Batch status:
REJECTED

Send notification to the creator:

Title:
"Batch Rejected"

Message:
"Batch {batchId} has been rejected."

Include the rejection reason when available.

The notification should allow the creator to open the Batch Details page and see the rejection reason.

--------------------------------------------------
LEVEL 1 REVERTS
--------------------------------------------------

When Level 1 reverts the batch:

Batch status:
REVERTED

Send notification to the creator:

Title:
"Batch Reverted"

Message:
"Batch {batchId} has been reverted. Please review and update the batch."

--------------------------------------------------
LEVEL 2 APPROVES
--------------------------------------------------

When Level 2 approves:

Batch status:
APPROVED / FULLY_APPROVED

Send notification to the creator:

Title:
"Batch Fully Approved"

Message:
"Batch {batchId} has been fully approved."

--------------------------------------------------
LEVEL 2 REJECTS
--------------------------------------------------

When Level 2 rejects:

Batch status:
REJECTED

Send notification to the creator:

Title:
"Batch Rejected"

Message:
"Batch {batchId} has been rejected."

Include the rejection reason.

--------------------------------------------------
LEVEL 2 REVERTS
--------------------------------------------------

When Level 2 reverts:

Batch status:
REVERTED

Send notification to the creator:

Title:
"Batch Reverted"

Message:
"Batch {batchId} has been reverted. Please review and update the batch."

==================================================
3. PAYMENT DATE NOTIFICATIONS
==================================================

Implement automatic payment-date reminder notifications.

Use the existing batch paymentDate field.

When the payment date is approaching, create a notification for the appropriate responsible users according to the existing business rules.

For example:

3 days before:

"Payment Date Approaching"

"Payment date for batch {batchId} is in 3 days."

1 day before:

"Payment Date Tomorrow"

"Payment for batch {batchId} is scheduled for tomorrow."

IMPORTANT:
- Do not notify every user.
- Notify only the appropriate creator/approver/responsible user according to the application's business rules.
- Do not create duplicate reminders for the same batch and reminder period.
- Do not send reminders for already completed/cancelled batches.

Use a backend scheduled job/scheduler for this.
Do NOT implement payment-date timers only in the frontend.

==================================================
5. BACKEND APIs
==================================================

Create/reuse these APIs:

GET /api/notifications

Return notifications belonging only to the currently authenticated user.

GET /api/notifications/unread-count

Return:

{
  "count": 3
}

PUT /api/notifications/{notificationId}/read

Mark the notification as read.

PUT /api/notifications/read-all

Mark all notifications for the logged-in user as read.

IMPORTANT:
Never accept a userId from the frontend to determine whose notifications are returned.

Get the authenticated user from the existing Spring Security/authentication mechanism.

==================================================
6. NOTIFICATION SERVICE
==================================================

Notification creation must happen in the backend service layer after a workflow operation succeeds.

Example:

Submit Batch
     ↓
Update batch status
     ↓
Determine Level 1 approver
     ↓
Create notification for Level 1 approver

Level 1 Approves
     ↓
Update batch status
     ↓
Determine Level 2 approver
     ↓
Create notification for Level 2 approver
     ↓
Notify creator

Reject/Revert
     ↓
Update batch
     ↓
Create notification for creator

If the batch operation fails, do NOT create a notification.

9. DUPLICATE BATCH
==================================================

Ensure the duplicate batch functionality works correctly with notifications.

When a rejected batch is duplicated:

- Generate a new unique Batch ID.
- Treat the duplicate as a new batch.
- Do not copy the old notification history.
- Do not copy the rejected status.
- Do not notify approvers immediately.
- Only create approval notifications when the new batch is actually submitted for approval.
